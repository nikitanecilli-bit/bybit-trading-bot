# Проверка временной привязки Open Interest (OI)

## Цель

Проверить чувствительность Oliver v6.1 к временной привязке Open Interest. Это исследовательский тест, а не автоматическое доказательство look-ahead bias.

## Что добавлено

- `oi_timing_sensitivity.py` загружает один фиксированный интервал данных и сравнивает два варианта на одной и той же истории:
  - `raw_oi`: OI сопоставлен с исходными временными метками;
  - `oi_lag_1bar`: исходный ряд OI сдвинут на одну 15-минутную свечу назад до расчёта `oi_mom_1` и `oi_mom_4`.
- Рассчитываются метрики модулей `M4_full_h1` (пробои с OI) и `M6_router` (комбинированный маршрутизатор), а при нескольких инструментах — синхронный портфель.
- Используется только dev-период до `--vault-start-date`; Vault не оценивается и не используется для настройки.
- Скрипт отказывается считать сравнение при покрытии native Mark Price ниже 99% или OI ниже 95%.
- Добавлен CLI-флаг `--oi-lag-bars` в исследовательскую копию движка для дополнительных экспериментов.

## Что говорят документы Bybit

Документация endpoint `/v5/market/open-interest` описывает поле `timestamp` как миллисекундную временную метку, но не объясняет в достаточной степени, является ли это временем начала/окончания 15-минутного интервала или точным временем замера. Поэтому вопрос остаётся открытым и требует теста чувствительности и/или подтверждения семантики у биржи.

## Локальная проверка

- `py_compile` для исследовательского движка и тестового скрипта — PASS.
- Регрессионные тесты P0 и тесты OI-lag — 8/8 PASS.
- Выполнен smoke-test на синтетических данных, чтобы проверить расчёт и CSV-отчёт. Он не является рыночным результатом и не доказывает утечку.

## Как запустить в Google Colab

После загрузки и распаковки архива:

```bash
python -m py_compile Oliver_fixed_research_p0_oi_lag.py oi_timing_sensitivity.py
pytest -q test_oliver_p0_research.py test_oliver_oi_lag.py
python oi_timing_sensitivity.py \
  --symbols BTCUSDT,ETHUSDT,SOLUSDT \
  --start-date 2023-01-01 \
  --end-date 2026-01-01 \
  --vault-start-date 2025-07-01 \
  --capital 1000 \
  --no-cache \
  --out oi_timing_sensitivity.csv
```

Первый запуск скачивает данные для фиксированного окна. Повторный запуск можно выполнить без `--no-cache`, чтобы обе версии использовали один и тот же кэш. Если API не отдаёт достаточную историю OI или native Mark Price, скрипт должен остановиться, а не выдавать сравнение на неполных данных.

## Как интерпретировать

- Существенное падение результата при сдвиге OI означает, что стратегия чувствительна к таймингу этого признака.
- Само по себе это **не доказывает** утечку: лаг меняет информационное содержание сигнала и может просто ухудшать своевременность.
- Если исходная метка OI оказывается недоступной на момент принятия решения, исходный вариант нужно сдвинуть/пересчитать до подтверждённого времени доступности.
- Если оба варианта убыточны или имеют слишком мало сделок, вывод об edge делать нельзя.
- Не подбирать пороги на Vault и не переносить результат в live до проверки многолетнего out-of-sample.
