# Рабочие правила проекта — Bybit Trading Bot

## Утверждённый режим работы

**Режим:** максимальная автономность.  
**Вычислительный бюджет:** сбалансированный.  
**Статус:** подтверждено пользователем 2026-11-02.

Ассистент самостоятельно ведёт исследовательский процесс без запроса подтверждения каждого промежуточного шага: изучает код и артефакты, формирует и ранжирует гипотезы, выбирает следующий эксперимент, запускает безопасные проверки и GitHub Actions, анализирует результаты, обновляет журнал экспериментов и предлагает следующий обоснованный шаг.

## Границы автономности и безопасность

- Не размещать реальные ордера и не подключать торговлю к реальному капиталу в рамках исследовательских задач.
- Не менять молча базовую стратегию, торговую логику или production-конфигурацию. Исследования проводить в research-ветках и отдельных диагностических модулях.
- Не удалять и не перезаписывать исходные данные, результаты, holdout-наборы и экспериментальные артефакты.
- Не считать положительный результат доказательством edge без проверки вне выборки, учёта комиссий, проскальзывания, funding и реалистичности исполнения.
- При существенном изменении архитектуры, риска реального капитала, секретов/ключей, live-режима или необратимом действии остановиться и запросить явное разрешение пользователя.
- Не маскировать неопределённость: разделять подтверждённые факты, гипотезы, ограничения данных и открытые вопросы.

## Сбалансированное использование вычислений

Перед дорогим backtest сначала выполнять дешёвые проверки:
1. Проверка схемы, полноты, временных меток и качества данных.
2. Проверка кода, конфигурации, утечек будущего и корректности исполнения.
3. Быстрые диагностические срезы и sanity-check на небольшом наборе.
4. Только затем — полный walk-forward / portfolio backtest, если результат может изменить решение.

Не запускать повторный тест без конкретной причины: новая гипотеза, исправление дефекта, изменённая методика/данные или проверка воспроизводимости. Не плодить сетки параметров без предварительного обоснования. Предпочитать один изолированный фактор за эксперимент и минимальный набор сравнений, достаточный для ответа.

## Обязательный стандарт каждого эксперимента

Фиксировать в `docs/research/EXPERIMENT_LEDGER_RU.md`:
- ID эксперимента, дату, Git commit SHA и workflow run ID;
- гипотезу и заранее сформулированный критерий успеха/отказа;
- инструменты, таймфрейм, временные границы, train/validation/holdout;
- конфигурацию, версию движка, источник и качество данных;
- количество сделок, gross/net PnL, комиссии, slippage, funding, PF, drawdown, expectancy в R/bps;
- результаты по каждому хронологическому периоду и инструменту, включая убыточные;
- ограничения модели исполнения, размер выборки и неопределённость;
- решение: принять к следующей проверке, отклонить или оставить открытым.

Не подменять portfolio-level результат суммой независимых инструментальных прогонов. Отмечать множественное тестирование, selection bias и любые оптимистичные допущения fill-модели. Holdout/lockbox не использовать для подбора параметров.

## Принцип продолжения

После каждого завершённого этапа самостоятельно выбирать следующий наиболее информативный и экономически оправданный шаг. Если данных недостаточно, сначала устранять конкретный пробел, а не запускать широкий перебор. Пользователю сообщать кратко: что проверено, что установлено, насколько надёжен вывод, что будет сделано дальше и какие действия требуют его решения.


## Расширенное разрешение пользователя на автономную работу

**Подтверждено пользователем 2026-11-02:** полная автономность в рамках безопасной исследовательской работы. Не ждать подтверждения для самостоятельных решений и действий, которые можно выполнить в репозитории и GitHub Actions без участия пользователя.

- Не прекращать исследовательский процесс только потому, что workflow ещё выполняется. После запуска проверять статус, получать логи/артефакты, дожидаться завершения доступными средствами и продолжать анализ.
- Не объявлять задачу завершённой по факту успешного старта workflow. Нужны завершённый статус, проверка job steps, артефактов и содержимого результатов.
- Если запуск завершился ошибкой, диагностировать её по логам; исправлять исследовательский код в research-ветке и повторять только необходимую часть, если это возможно.
- Если тест ещё выполняется, переключаться на независимую полезную работу (аудит кода, проверка методики, анализ предыдущих результатов), затем возвращаться к ожиданию. Не запускать конкурирующие дублирующие тесты.
- Самостоятельно создавать диагностические скрипты, отчёты, тесты и обновлять журнал экспериментов в research-ветке, если это не меняет live-торговлю и не затрагивает production.
- Не спрашивать пользователя о выборе между техническими вариантами, если можно выбрать консервативный, воспроизводимый вариант и объяснить его в отчёте.
- Запрашивать пользователя только при реальном внешнем блокере: недоступные приватные данные/учётные записи, необходимость предоставить секрет/доступ, неоднозначное бизнес-решение, изменение риска реального капитала или необратимое действие вне исследовательской ветки.
- Если среда не позволяет продолжать ожидание или выполнять фоновые действия после завершения текущего ответа, прямо сообщать это ограничение; не обещать непрерывную работу в фоне и не имитировать ожидание.

Это разрешение не отменяет защитные ограничения выше: никаких реальных ордеров, публикации секретов, изменения production/live-параметров или удаления исходных данных без отдельного согласования.

## Стратегический приоритет: не подключать Bybit API / runner до доказательства edge

**Подтверждено пользователем 2026-11-03.** До обнаружения устойчиво прибыльной стратегии запрещено тратить исследовательский ресурс на регистрацию self-hosted runner, подключение Bybit API или сбор новых биржевых архивов. Эти задачи не являются текущим bottleneck и не должны подменять поиск торгового преимущества.

- Использовать уже имеющиеся исторические OHLCV-архивы и локальный backtest engine.
- Сначала добиться положительного net expectancy после заранее зафиксированных реалистичных комиссий и стресс-издержек, затем подтвердить результат на независимых хронологических периодах и shared-capital portfolio replay.
- Не выбирать стратегию по сумме независимых per-symbol прогонов или по одному удачному fold.
- К Bybit API / runner возвращаться только после появления кандидата, который прошёл исследовательские критерии устойчивости, и если конкретная проверка исполнения/данных действительно нужна для следующего этапа.
- Никаких реальных ордеров на любом этапе без отдельного явного разрешения пользователя.
