## Finding

Before this correction, `validate_selection_provenance()` checked the hashes and sizes of every code file already listed in the frozen selection manifest. It did not require the current replay dependency list to contain exactly the same paths.

Consequently, if a new replay-critical dependency was added after Top-5 selection, the old manifest could pass: all previously recorded files remained unchanged, while the new dependency was not represented in the manifest. This was a confirmed provenance-validation gap. It could allow a replay to run with a dependency set different from the one used to freeze the selected universe.

## Correction

In `scripts/run_h1_shared_capital_portfolio_validation.py`, `validate_selection_provenance()` now:

1. Strictly validates each recorded/current code provenance row (`path`, `sha256`, non-negative integer `size_bytes`).
2. Rejects duplicate dependency paths in either list.
3. Requires exact equality between the recorded and current dependency path sets.
4. Reports missing and newly added dependencies and requires the train-only selector to be rerun.
5. Compares SHA-256 and file size for every path after exact-set validation.

This is fail-closed. It does not change signal generation, position sizing, execution, costs, portfolio risk, or production defaults.

### Shared-capital ordering and risk allocation — code-reviewed

The H1 runner supplies a sorted, synchronized five-symbol basket to
`run_simulation_pass()`. For each completed H1 timestamp, the engine:
- computes portfolio adverse marks for all symbols before processing any one
  symbol;
- preallocates the remaining 2% portfolio stop-risk budget across eligible
  pending entries, with at most five open positions;
- ranks scarce slots by signal priority/volume ratio, then symbol as a stable
  tie-breaker; and
- processes the complete pending batch using the preallocated equity and risk
  shares, so iteration order cannot consume another symbol's risk budget.

Existing regression `test_simultaneous_entries_share_risk_budget_independent_of_symbol_order`
checks reversed symbol iteration and confirms the total risk remains within
200 USDT on a 10,000 USDT account. This is a deterministic engine test, not
evidence of exchange execution or profitability.

### Limit-fill model — remaining material limitation

The H1 wrapper places a buy limit 20 bps below the signal close, waits up to
three eligible H1 candles, and requires either a marketable opening gap or
five bps of OHLC penetration beyond the limit. Marketable-at-open entries are
classified as taker; intrabar penetration fills are credited at the limit and
treated as maker.

The H1 runner does **not** consume historical bid/ask or L2 events. It cannot
verify queue position, spread crossing, partial fills, cancellations ahead,
or adverse selection. The repository's aggregate-L2 queue primitives are a
separate research probe; they are not wired into the H1 strategy replay and
are not a fill-rate or PnL result. Accordingly, the current H1 intrabar maker
fill assumption remains optimistic and must be stress-tested before any
positive result can be treated as credible.

### Result retention

The H1 runner writes every fold/config/cost result row to the CSV and stores
the full `result_rows` array in the JSON manifest. Paired summaries are
additional comparisons; they do not replace or filter the raw rows. The
train-only selector also retains evaluated candidates with exclusion reasons,
rather than promoting weak or negative candidates into the Top-5.

## Same-timestamp portfolio close ordering — confirmed defect corrected — 2026-11-04

### Reproduction

A deterministic H1 regression used two open long positions and synchronized Last/Mark candles:
- both positions were marked at the same Mark Price boundary;
- the BTC Last candle closed below its Mark adverse low, while the ETH Last candle closed above its Mark adverse low;
- both positions reached a time-stop close at the same H1 timestamp;
- the emergency kill-switch threshold was set between the transient drawdowns created by processing the losing close first versus the profitable close first.

Before the fix, the loss-first order crossed the kill-switch threshold during the per-position close accounting while the win-first order did not. The second symbol could consequently be forcibly closed under a different reason/price. The regression failed on the pre-fix implementation, proving the effect with the engine's own Last/Mark mark construction rather than only an artificial direct-ledger sequence.

### Correction

Synchronized replay now treats all symbol executions on one candle-close timestamp as a batch for portfolio stop evaluation:
- the initial portfolio-wide adverse Mark/Last check still runs before any symbol is processed;
- while each symbol's position/order lifecycle is processed, closed PnL and remaining-position MTM are reconciled, but daily/emergency drawdown latches are not evaluated after each individual close;
- after all active symbols have been processed, the engine performs one portfolio-wide MTM/drawdown evaluation;
- if that final same-timestamp snapshot newly trips the emergency kill-switch, residual positions are flattened using the already prepared Last Price risk marks, while a precomputed liquidation exit retains priority;
- dense and sparse shared-capital replay use the same batch boundary;
- close accounting retains its normal immediate risk-evaluation behavior outside synchronized replay batches.

This avoids inventing an intra-bar ordering between independent symbols and prevents an intermediate mark-to-execution reconciliation from changing the exit treatment of later symbols solely due to list order. The final portfolio snapshot still evaluates real net realized/unrealized PnL and can trigger the kill-switch; this is not a relaxation of the risk limit.
