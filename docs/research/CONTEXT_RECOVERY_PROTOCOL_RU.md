# Протокол восстановления контекста — Bybit Trading Bot

> Статус: рабочий протокол. Назначение — быстро и доказательно продолжать исследование в новом чате без переноса длинной переписки.
> Репозиторий: `nikitanecilli-bit/bybit-trading-bot`.
> Документ создан в отдельной ветке `docs/context-recovery-protocol` на основе `research/market-regime-v1-main`. Не считать его автоматически слитым в рабочую ветку.

## 1. Команда запуска новой сессии

Пользователь может написать:

**«Продолжить Bybit Trading Bot. Восстанови состояние проекта».**

Не просить пользователя повторять рабочие правила, цели или историю экспериментов, пока соответствующие файлы доступны в репозитории.

## 2. Обязательный bootstrap новой сессии

Выполнять по порядку, используя GitHub как источник актуального состояния.

1. Найти и подтвердить рабочую ветку по действующим инструкциям. Ожидаемая ветка из последнего handoff: `research/market-regime-v1-main`, но это только подсказка, не доказательство.
2. Получить текущий HEAD SHA рабочей ветки и дату последнего коммита. Не подменять HEAD:
   - SHA из старого чата;
   - SHA из handoff, если он обозначен как snapshot;
   - последним коммитом репозитория в целом (он может принадлежать другой ветке).
3. Проверить открытые PR, связанные с рабочей веткой, особенно PR #4. Зафиксировать base/head и не выполнять merge/rebase автоматически.
4. Прочитать именно из актуальной рабочей ветки:
   - `AGENTS.md`;
   - `PROJECT_WORKING_RULES_RU.md`;
   - `docs/README_RU.md`;
   - `docs/research/EXPERIMENT_LEDGER_RU.md`;
   - `docs/research/SESSION_HANDOFF_2026-11-04_RU.md`;
   - `docs/research/CONTINUATION_CHECKPOINT_2026-11-04_RU.md`;
   - этот протокол, если он уже перенесён в рабочую ветку.
5. Проверить Actions runs, относящиеся к актуальному HEAD и недавним исследовательским/CI-коммитам. Разделять:
   - workflow запущен;
   - workflow завершён;
   - job успешен;
   - нужные тесты реально исполнены;
   - артефакты и их содержимое проверены.
6. Найти в Experiment Ledger соответствующие эксперименты и артефакты. Не повторять завершённые проверки без конкретной причины.
7. Составить краткий внутренний state summary и продолжить с ближайшей безопасной задачи из handoff/checkpoint.

### Если часть GitHub-данных недоступна

- Не выдумывать HEAD SHA, workflow status, содержимое артефактов или состояние PR.
- Явно указать, что именно не удалось подтвердить, и использовать последний документированный snapshot только как историческую справку.
- Если инструмент не предоставляет чтение branch ref/HEAD, это ограничение надо назвать; не выдавать поиск последних коммитов репозитория за проверку HEAD нужной ветки.
- Не просить пользователя вручную копировать данные, пока не исчерпаны доступные GitHub-инструменты.

## 3. Короткий отчёт пользователю после восстановления

Не пересказывать весь handoff. Достаточно:

- **Рабочая ветка / HEAD:** SHA и способ подтверждения; если не подтверждено — прямо написать.
- **Последний проверенный CI:** run ID, commit, conclusion и фактически выполненные тесты.
- **Текущая исследовательская точка:** 1–3 предложения.
- **Ограничения / блокеры:** только актуальные.
- **Следующее действие:** один конкретный безопасный шаг.

## 4. Правила экономии контекста

- GitHub и исследовательские документы — долговременный источник правды; чат — временное рабочее пространство.
- Не копировать в новые чаты длинные логи, полные CSV, большие diff или историю сообщений, если они доступны в GitHub/artifacts.
- В чат переносить только короткие выводы, точные ссылки, SHA/run ID и вопросы, которые требуют решения.
- Для анализа артефактов сначала проверять наличие и метаданные; извлекать только нужные файлы/столбцы/диапазоны.
- Не повторять уже подтверждённые тесты и эксперименты. Перед новым экспериментом сверять ID/гипотезу с Experiment Ledger.
- Не дублировать полные правила автономности в каждом запросе: они закреплены в `PROJECT_WORKING_RULES_RU.md`.
- Не пытаться «очистить» историю открытого чата как способ освободить контекст: новый чат с компактным восстановлением — более надёжный путь.

## 5. Когда обновлять handoff

Обновлять `SESSION_HANDOFF` и/или `CONTINUATION_CHECKPOINT` после каждого значимого этапа, если изменилось хотя бы одно из следующего:

- рабочая ветка или важный commit SHA;
- завершённый CI или подтверждённый regression test;
- новый дефект, исправление или ограничение методики;
- результат эксперимента или решение по гипотезе;
- порядок следующих задач или исследовательские gate;
- внешний блокер или изменение разрешений пользователя.

Запись должна быть компактной и проверяемой: дата, commit SHA, файлы/функции, evidence, статус проверки, ограничения, следующий шаг. Не переписывать историю задним числом; добавлять датированное обновление.

## 6. Незавершённые workflow и сессии

- Если workflow выполняется, продолжать независимую безопасную работу и возвращаться к проверке статуса, пока текущая сессия и инструменты позволяют.
- Не утверждать, что агент продолжит работу после завершения ответа или в фоне.
- При новом чате сначала заново проверить состояние workflow; не считать прошлое сообщение доказательством завершения.
- Не запускать дублирующий workflow только ради ожидания.

## 7. Неизменяемые проектные ограничения

До изменения этих правил самим пользователем действуют ограничения из `AGENTS.md`, `PROJECT_WORKING_RULES_RU.md` и актуального handoff. В частности:

- никаких реальных ордеров, live-режима, account/private API или API-ключей;
- не скачивать новые market archives и не запускать collectors, пока действуют соответствующие data gates;
- не запускать market/PnL backtests, parameter sweeps или strategy replay до снятия maker-execution/data gate;
- не менять `main`, production, базовую стратегию или движок без отдельного обоснования;
- не удалять и не перезаписывать исходные данные, holdout и исторические артефакты;
- разрешены безопасные статические аудиты, provenance review, deterministic tests и точечные исправления подтверждённых дефектов;
- не считать OHLCV limit-touch fill доказательством maker execution;
- не объявлять CI успешной валидацией без проверки фактически выполненных шагов и артефактов.

## 8. Минимальный шаблон записи в handoff

Добавлять только при наличии реального изменения:

```markdown
## Session update — YYYY-MM-DD (краткая тема)

- Рабочая ветка / commit SHA:
- Изменённые файлы и функции:
- Причина / подтверждённый дефект:
- Regression tests и фактический результат:
- CI run / conclusion / проверенные steps:
- Артефакты и ссылки:
- Ограничения / что НЕ доказано:
- Следующий безопасный шаг:
- Подтверждение отсутствия запрещённых действий (PnL/API/live/main), если релевантно:
```

## 9. Важная оговорка о переносе протокола

Этот файл создан в отдельной документационной ветке, чтобы не менять исследовательскую ветку без проверки её актуального состояния. Перед использованием как обязательного project policy его следует перенести в `research/market-regime-v1-main` отдельным reviewed commit/PR. До этого момента его можно использовать как предложенный протокол, но действующими источниками правил остаются файлы, перечисленные в разделе 2.
