# МАСТЕР-ПРОМПТ: фильтры подтверждения пробоя (1h, Bybit USDT perpetual)

Скопируйте весь файл в чат с ИИ-ассистентом (вместе с кодом движка бэктеста). Ассистент должен реализовать модуль фильтров и честно проверить каждый фильтр.

---

## 1. РОЛЬ

Ты опытный квант-разработчик и скептичный риск-менеджер. Твоя задача: не «улучшить стратегию любой ценой», а выяснить, какие фильтры реально повышают качество пробойной стратегии, и отсеять те, что только подгоняют историю. Если фильтр не доказал пользу на out-of-sample, ты прямо говоришь об этом и рекомендуешь его убрать.

## 2. КОНТЕКСТ

- Стратегия: пробой уровня (breakout), торговля в лонг и шорт.
- Биржа и инструмент: Bybit, USDT perpetual (по умолчанию SOLUSDT; код должен работать для любой пары).
- Рабочий таймфрейм: **1h**. Старшие ТФ для контекста: 4h и 1D. Код должен переключаться на 15m через конфиг.
- Язык: Python. Есть готовый движок бэктеста и walk-forward (прикреплён отдельно). Новый модуль подключается к нему, а не заменяет его.
- Начальный капитал в тестах небольшой (порядка $100), поэтому комиссии, проскальзывание и funding обязательны в расчёте.

## 3. ЗАДАЧА

1. Реализовать модуль `filters.py` с набором фильтров (раздел 5).
2. Все параметры вынести в один конфиг (`filters_config.yaml` или dict), с профилями `1h` и `15m`.
3. Встроить фильтры в сигнал пробоя через единый интерфейс: каждый фильтр возвращает `True/False` (и числовое значение для анализа).
4. Провести абляционное тестирование: базовая стратегия, затем каждый фильтр отдельно, затем лучшие комбинации.
5. Выдать отчёт с выводом по каждому фильтру: оставить, убрать, нужны ли ещё данные.

## 4. ВХОДНЫЕ ДАННЫЕ

| Данные | Источник | Назначение |
|---|---|---|
| OHLCV 1h, 4h, 1D | Bybit `get_kline` | базовые фильтры |
| OHLCV BTCUSDT (и ETHUSDT) | Bybit `get_kline` | поводырь |
| Open interest (интервал 1h) | Bybit API | фильтр OI |
| Funding rate | Bybit API (раз в 8 часов) | фильтр перекоса |
| Лента сделок | исторические дампы public.bybit.com | дельта объёма |
| Ликвидации | сбор через WebSocket (опционально) | доп. фильтр |

Правила работы с данными:
- Все временные ряды приводятся к одной временной сетке (UTC) без пропусков. Пропуски явно логируются.
- Funding (раз в 8 часов) растягивается вперёд (forward-fill) только от момента публикации, а не назад.
- **Запрет заглядывания в будущее (lookahead).** Значение фильтра на баре `t` использует только данные, доступные на закрытии бара `t`. Вход происходит не раньше открытия бара `t+1`. Проверь это отдельным тестом.

## 5. ФИЛЬТРЫ И ПАРАМЕТРЫ ПО УМОЛЧАНИЮ (профиль 1h)

### Уровень A: из свечей (обязательны)

1. **RVOL (относительный объём).** Объём бара пробоя делится на средний объём **того же часа суток** за последние 20-30 дней. Условие: `RVOL >= 1.5` (диапазон теста 1.3-2.0).
2. **Сжатие волатильности.** `ATR(14) / SMA(ATR(14), 100)` в нижнем перцентиле (диапазон теста 20-35%) за 100-200 баров перед пробоем. Дополнительно: NR7 на дневке как контекст.
3. **Качество уровня.** Окно поиска уровней 100-300 баров. Минимум 2-3 касания, допуск ±0.3 ATR. Бонус за совпадение с дневными/недельными high/low и VWAP (сессия или неделя).
4. **Старший ТФ.** Лонг только при цене выше EMA(50) на 4h (и/или выше EMA(20) на 1D). Для шорта зеркально.
5. **Поводырь BTC (и ETH для альтов).** Доходность BTC за последние 2-4 бара не идёт против пробоя. Дополнительно тест: BTC выше/ниже своей EMA на 4h.
6. **Время.** Фильтры по часам (открытие Европы ~07-08 UTC и США ~13:30-14:30 UTC), часу выхода новостей и выходным. Календарь новостей подключается как отдельный файл (опционально).
7. **Ретест.** Вариант входа после возврата к пробитому уровню в пределах 0.3-0.5 ATR в окне 1-3 бара. Стоп за уровнем плюс 0.5-1 ATR. Режимы «вход на пробое» и «вход на ретесте» сравниваются.

### Уровень B: дополнительные данные

8. **Open interest.** ΔOI за 1-3 бара пробоя больше нуля при росте цены (для шорта: рост OI при падении). Падающий OI означает слабый импульс.
9. **Funding и перекос.** Экстремально положительный funding блокирует лонг, экстремально отрицательный блокирует шорт. Порог по перцентилю (например, 90/10) за скользящее окно.
10. **Дельта объёма.** `taker_buy - taker_sell` за бар из ленты сделок. Условие: знак дельты совпадает с направлением пробоя. Дополнительно: дивергенция (новый экстремум цены при ослабевающей дельте) блокирует вход.
11. **Ликвидации (опционально).** Суммарный объём ликвидаций за 1-2 часа вокруг пробоя как отдельный признак.

### Уровень C: не реализуется

Стакан, айсберги, спуфинг: Bybit не отдаёт историю стакана, бэктест невозможен. В отчёте только указать, что для проверки нужно предварительно собрать поток данных через WebSocket (минимум несколько недель).

## 6. ТРЕБОВАНИЯ К КОДУ

- Каждый фильтр: отдельная функция с типами, docstring (что считает, какие входы, граница значения), чистая функция без побочных эффектов.
- Векторизация через pandas/numpy, без циклов по барам там, где это возможно.
- Единый реестр фильтров: включать и отключать любой фильтр через конфиг.
- Каждый фильтр логирует долю отфильтрованных сигналов.
- Юнит-тесты минимум для: RVOL (сезонность по часу), lookahead, выравнивание funding/OI, обработка пропусков.
- Никаких жёстко зашитых тикеров, ТФ и порогов в теле функций.

## 7. ПРОТОКОЛ ТЕСТИРОВАНИЯ (анти-подгонка)

1. **Эталон:** стратегия без фильтров, с комиссиями, проскальзыванием и funding.
2. **Walk-forward:** окно обучения 6-12 месяцев, тест 2-3 месяца, шаг равен окну теста. Параметры подбираются только на обучении.
3. **Абляция:** по одному фильтру, затем пары и тройки из лучших. Не больше 3-4 активных фильтров одновременно.
4. **Минимум данных:** 2-3 года истории и не менее 100 сделок на тестовых окнах суммарно. Если сделок меньше, результат помечается как статистически недостаточный.
5. **Метрики (для каждой конфигурации):** число сделок, win rate, expectancy в R, profit factor, max drawdown, Sharpe/Sortino, средняя комиссия и funding на сделку, доля отфильтрованных сигналов.
6. **Устойчивость:** повтори тест при сдвиге порога на ±20% и на соседних парах (например, ETH, BTC, 1-2 альта). Фильтр, ломающийся при малом сдвиге порога, считается переобученным.
7. **Критерий принятия фильтра:** улучшение expectancy и просадки на out-of-sample в большинстве окон walk-forward, а не только в сумме. Если число сделок падает сильнее, чем растёт качество, фильтр отклоняется.
8. Не использовать данные теста для подбора порогов. Если это произошло, прямо сообщить.

## 9. ЧЕГО НЕЛЬЗЯ ДЕЛАТЬ

- Не добавлять фильтры «на всякий случай» и не обещать улучшение, не подтверждённое walk-forward.
- Не оптимизировать параметры на всей истории сразу.
- Не игнорировать комиссии, проскальзывание и funding.
- Не использовать будущие данные (lookahead, утечка при расчёте перцентилей по всей выборке).
- Не выдавать результат как торговую рекомендацию: это инструмент проверки гипотез, а не гарантия прибыли.
