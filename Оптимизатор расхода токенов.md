# 5. Компонент №1. AI Snapshot


## Задача


Создать механизм формирования компактного представления торговой истории для передачи ИИ.


ИИ не должен получать полный журнал сделок, если для решения задачи достаточно агрегированных данных.


Ориентир:
- 1 000–2 000 токенов для стандартного Snapshot;
- расширенный режим по запросу;
- полный журнал остаётся доступен вычислительным инструментам, но не передаётся модели по умолчанию.


## Содержание Snapshot


Предусмотри следующие блоки:


### A. Общая статистика
- количество сделок;
- период исследования;
- gross PnL;
- net PnL;
- комиссии;
- slippage;
- expectancy;
- win rate;
- profit factor;
- максимальная просадка;
- среднее и медианное R;
- количество независимых наблюдений, если оно определимо.


### B. Временные закономерности
- день недели;
- час входа;
- час выхода;
- временные интервалы;
- количество сделок в каждой корзине;
- результаты по временным группам.


### C. Причины выхода
- Stop Loss;
- Take Profit;
- Time Exit;
- другие предусмотренные проектом категории.


### D. Корзины признаков
Для каждой корзины:
- название признака;
- границы;
- количество наблюдений;
- средний результат;
- медианный результат;
- доверительный интервал;
- MDE, если он рассчитан корректным методом;
- предупреждения о недостаточной статистической мощности.


### E. Качество данных
- пропущенные значения;
- дубликаты;
- подозрительные наблюдения;
- версия датасета;
- период данных;
- хэш данных;
- статус валидации.


## Два режима детализации


**Compact:**
- только агрегаты;
- только существенные отклонения;
- предупреждения;
- короткие выводы.


**Detailed:**
- расширенные таблицы;
- дополнительные разрезы;
- статистические подробности;
- ссылки на конкретные группы наблюдений.


Не выдавай статистическую значимость там, где её нельзя обосновать.


## Интерфейс


Подготовь механизм:


`generate_snapshot.py --mode compact`


и


`generate_snapshot.py --mode detailed`


Если в проекте есть веб-дашборд:
- добавь кнопку «Слепок для ИИ»;
- по нажатию формируй Compact Snapshot;
- предоставь возможность скопировать его в буфер обмена;
- не отправляй данные во внешние сервисы автоматически.


Если дашборда нет, создай CLI-интерфейс и опиши API для последующей интеграции.

# 6. Компонент №2. Causal Metrics Library


## Главная задача


Сделать невозможным получение стратегией будущих данных через стандартный интерфейс.


Стратегия должна получать только информацию, которая была доступна на момент принятия решения.


## Интерфейс данных


Предусмотри интерфейс типа:


`history(n)`


Он должен возвращать исключительно прошлые наблюдения относительно текущего момента симуляции.


Определи:
- временную семантику;
- правила обработки timestamp;
- правила сортировки;
- доступность текущей свечи;
- момент доступности признаков;
- правила обработки незакрытых свечей;
- правила обработки задержанных данных.


Не допускай скрытого доступа к полному DataFrame или будущим значениям.


Проверь не только очевидный look-ahead bias, но и:
- утечки при нормализации;
- утечки при feature engineering;
- утечки при построении таргетов;
- утечки при ресемплинге;
- утечки при использовании rolling statistics;
- утечки при подборе гиперпараметров;
- утечки между train/test;
- утечки через исполнение ордеров.


## Единая библиотека метрик


Все расчёты должны использовать единые определения:


- R;
- bps;
- проценты;
- USDT;
- gross PnL;
- net PnL;
- commission;
- slippage;
- expectancy;
- drawdown;
- Sharpe;
- Sortino;
- Profit Factor.


Определи единицы измерения, знаки, порядок применения издержек и формулы.


ИИ не должен самостоятельно переписывать формулы.


Все расчёты выполняются кодом.


Особое внимание:
- одинаковые единицы измерения;
- отсутствие двойного учёта комиссий;
- корректная обработка нулевых значений;
- корректная обработка пропусков;
- воспроизводимость вычислений.

# 7. Компонент №3. Numbers Linter


## Задача


Создать проверку численных утверждений, которые ИИ включает в свой отчёт.


Принцип:


ИИ получает результаты эксперимента в JSON и пишет выводы.


Линтер проверяет каждое численное утверждение по исходному JSON.


## Требования


1. Извлекать численные утверждения из отчёта.
2. Сопоставлять их с зарегистрированными показателями эксперимента.
3. Проверять единицы измерения.
4. Проверять округление и допустимые отклонения.
5. Проверять, не перепутаны ли gross и net.
6. Проверять, не перепутаны ли проценты и bps.
7. Проверять, не используются ли показатели из другого запуска.
8. Отмечать числа, которые невозможно подтвердить.
9. Формировать машинно-читаемый JSON с результатами проверки.


Пример статусов:


- VERIFIED — подтверждено;
- MISMATCH — значение не совпадает;
- UNVERIFIED — источник отсутствует;
- STALE — результат устарел;
- UNIT_ERROR — ошибка единиц измерения.


Линтер не должен пытаться угадывать правильное значение.


Если число отсутствует в исходных данных, оно не может считаться подтверждённым.


Предусмотри защиту от ситуаций, когда ИИ:
- округляет некорректно;
- меняет знак;
- смешивает разные эксперименты;
- приводит устаревшие показатели;
- выдаёт статистические оценки за фактические результаты.

# 8. Контроль актуальности результатов


Реализуй хэш допущений эксперимента.


В него должны входить:
- версия данных;
- версия симулятора;
- комиссия;
- модель исполнения;
- slippage;
- параметры стратегии;
- версия библиотеки метрик;
- настройки статистических тестов.


При изменении любого существенного параметра предыдущие результаты должны получать статус STALE.


Предусмотри обязательную проверку:
- наличия карточки эксперимента;
- целостности lockbox;
- актуальности trials.csv;
- соответствия JSON-результата текущей конфигурации.


Не обходи существующие механизмы защиты.


Если lockbox отсутствует или нарушен, инструмент должен завершать работу с понятной ошибкой.

# 9. Автоматические тесты


Создай тесты, которые не требуют заранее заданного правильного результата стратегии.


Обязательные проверки:


| Тест | Ожидаемое поведение |
|---|---|
| Масштабирование цен | R не меняется при пропорциональном изменении цены и соответствующих параметров |
| Зеркальный ряд | Результаты корректно отражаются при преобразовании направления и данных |
| Рост издержек | Net PnL не улучшается при увеличении одинаково применяемых издержек |
| Эталонный симулятор | Результаты совпадают на согласованном тестовом наборе |
| Плацебо | Перемешанные метки не дают устойчивого предсказательного эффекта сверх ожидаемого случайного уровня |


Дополнительно:
- тест на look-ahead bias;
- тест на утечку при нормализации;
- тест на timestamp;
- тест на двойной учёт комиссий;
- тест на единицы измерения;
- тест на устаревшие результаты;
- тест на некорректные числа в отчёте.


Для каждого теста укажи:
1. Что именно проверяется.
2. Почему это важно.
3. Какие данные используются.
4. Что считается успешным результатом.
5. Какие ограничения имеет тест.


Не объявляй отсутствие утечек доказанным только на основании прохождения нескольких unit-тестов.
