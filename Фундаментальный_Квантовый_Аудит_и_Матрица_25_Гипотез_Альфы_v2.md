### 0.2 Десять правил для ИИ-ассистента (минимальный контракт)

1. **Нет цифры без `run_id`.** Любое число эффекта (PF, ожидание, win rate) берётся только из выполненного прогона с записанным конфигом и датасетом — не «из памяти» и не «на глаз».
2. **Только net.** Метрики считаются после комиссий, проскальзывания и funding. Gross показывается лишь рядом с разложением издержек.
3. **Каждый тест — запись в реестр попыток** (`trials.csv`). Число проверенных вариантов нужно для поправки на множественное тестирование.
4. **Lockbox неприкосновенен.** Финальный отрезок истории (и данные, появившиеся после даты отсечения знаний модели) открывается один раз, по решению человека.
5. **Признаки — только «as-of» момент решения** (закрытые бары ≤ t). Объём текущего бара при исполнении лимитки, ΔOI до закрытия бара, MFE после входа — утечки.
6. **Исполнение — пессимистично:** лимитка исполняется только при проходе цены сквозь уровень; стоп — taker с проскальзыванием; при неоднозначности внутри бара стоп срабатывает раньше тейка.
7. **Время.** Хранение в UTC; сессии определяются по локальному времени бирж через tz-базу, а не «магическими» UTC-окнами.
8. **Результат — это набор:** ожидание в R и в bps + доверительный интервал + N_eff + стресс ×1.5/×2 издержек + устойчивость параметров. Одна метрика выводом не является.
9. **Неоднозначность фиксируется письменно** (единицы, таймстемп, определение R) и проверяется тестом — не угадывается.
10. **ИИ — исследователь и инженер, а не «оракул цен» и не live-трейдер.** В бою решения принимает детерминированный, протестированный код с жёсткими лимитами риска (см. 7.8).

### 0.3 Карта документа

I — экономика издержек • II — дайджест доказательств • III — стандарт доказательств • IV — гипотезы (карточки) • V — приоритеты • VI — журнал, майнинг правил, контур изменений • VII — протокол работы ИИ • VIII — план • Приложения: A — источники, B — исправления v1, C — шаблоны.

Соответствие частям v1: II (25 гипотез) → IV; III (матрица) → V; IV (ИИ-контур) → VI; V (план) → VIII. Части II, III и VII — новые. В Приложении B пометка «(v1)» означает нумерацию v1, без пометки — нумерацию v2.

Экономия контекста: ИИ достаточно загружать «Часть 0 + нужную карточку из IV + Часть III», а не весь файл (подробнее — 7.7).

Имена: стратегические модули — **S1** (Momentum Breakout) и **S2** (Mean-Reversion / Range Fade); гипотезы — **H-xx** и **R-xx**. В v1 модули назывались «H-1/H-2» и путались с гипотезами H-01/H-02 `[FIX]`.

## ЧАСТЬ I. ДИАГНОЗ: ЭКОНОМИКА ИЗДЕРЖЕК (исправленная)

### I.1 Проверенные факты о стоимости торговли на Bybit

- **Комиссии USDT-перпетуалов** (обычный аккаунт, не VIP): taker `0.055%`, maker `0.020%` `[VERIFIED]` [S1]. Ставки из v1 верны.
- **Maker — это комиссия, а не доход.** Формулировка v1 «превратить комиссию в источник дохода» верна только для отрицательных maker-тарифов (программы маркет-мейкеров, высшие уровни) — для розничного объёма нереалистично. Реальная цель — *снизить* издержки.
- **Стоп-лосс = taker.** Рыночный стоп платит taker-комиссию и проскальзывание. Круг «maker + maker» достижим только на сделках, закрытых лимитным тейком; проигрышные закрываются по taker.
- **Funding — реальный компонент издержек.** По умолчанию расчёт в `00:00 / 08:00 / 16:00 UTC`; платят и получают только держатели позиции в момент расчёта; у отдельных контрактов интервал 1/2/4 ч, а у лимита ставки возможен переход на часовой `[VERIFIED]` [S2]. В v1 funding в PnL не учитывался `[FIX]`.
- **Игра с отрицательной суммой** `[VERIFIED логикой]`: до комиссий торговля — игра с нулевой суммой (выигрыш одного = проигрыш другого), после комиссий и спреда сумма отрицательна.

### I.2 Единая формула издержек

Обозначения:
- `Δstop = |P_entry − P_stop| / P_entry` — относительная ширина стопа;
- `c_rt = fee_in + fee_out + slip_in + slip_out + funding_paid` — полная круговая издержка в долях номинала;
- `R = notional × Δstop` — риск при срабатывании стопа, USDT.

$$\text{cost}_R=\frac{c_{\text{rt}}}{\Delta_{\text{stop}}},\qquad E[R_{\text{net}}]=E[R_{\text{gross}}]-E[\text{cost}_R]$$

Издержка в R **не зависит от плеча и размера позиции** — только от отношения «издержка / ширина стопа» `[VERIFIED арифметикой]`:

| Круговая издержка `c_rt` | стоп 0.4% | стоп 0.8% | стоп 1.5% | стоп 2.5% |
| :-- | :-: | :-: | :-: | :-: |
| maker + maker: 0.04% | 0.10R | 0.05R | 0.03R | 0.02R |
| maker + taker: 0.075% | 0.19R | 0.09R | 0.05R | 0.03R |
| taker + taker: 0.11% | 0.28R | 0.14R | 0.07R | 0.04R |
| taker + taker + проскальзывание: 0.16% | 0.40R | 0.20R | 0.11R | 0.06R |
| допущение v1: 0.20% | 0.50R | 0.25R | 0.13R | 0.08R |

**[FIX] Противоречие v1.** Одна и та же ситуация (стоп 0.40%) в Части I v1 оценена как `0.30R` (издержка $30 / плановый риск $100), как `0.40R` (0.16% / 0.40%) и по сути как `0.50R` (0.20% / 0.40%). Причина: при ограничении плеча позиция $15 000 вместо расчётных $25 000, и фактический риск на стопе — `$15 000 × 0.4% = $60`, а не $100; издержка $30 — это `0.5R`. **Правило: R всегда считается по фактическому риску на стопе, а не по плановому.**

**Условие безубыточности в bps.** Средний валовый ход, который стратегия забирает на сделку, должен превышать `c_rt` (в bps номинала). При `c_rt` 16–20 bps и типичном диапазоне 15-минутного бара порядка 25–35 bps (оценка v1, `[HYPOTHESIS]`) издержки сопоставимы с размером типичного бара — отсюда структурная проблема коротких пробоев.

### I.3 Какие рычаги снижают издержки (в порядке силы)

1. **Оборот и горизонт.** Издержка платится за каждую сделку; многодневные модели платят её на порядки реже. Для них есть опубликованные результаты (ансамбль Donchian на дневных барах [S8]) — см. R-01.
2. **Ширина стопа относительно издержки** (`cost_R`) — но ширина стопа меняет саму стратегию, это не «бесплатный» рычаг (см. H-01).
3. **Роль исполнения** (maker вместо taker): экономия `0.035 п.п.` комиссии + проскальзывание на каждой maker-ноге; стопы остаются taker (H-02…H-04, R-04).
4. **Селективность:** отбрасывать сделки с плохим `cost_R` или низким ожиданием (H-01, H-17, H-19).
5. **Размер через волатильность** (R-02), а не через «риск / ширина стопа».

### I.4 Три причины убытков v1: статусы

1. **«Инфляция плеча на узком стопе»** — механизм верен математически; числа — по I.2.
2. **«Токсичный поток на пробоях»** `[NARRATIVE]` — правдоподобно, но «убирают заявки и переставляют выше на 0.15–0.35%» на свечах не наблюдается. Измеримый след — сдвиг mid-цены против вас в первые секунды/минуты после рыночного входа на пробое (adverse selection, bps); для этого нужен журнал «сигнал → исполнение» (Часть VI).
3. **«Симметричная торговля в асимметричной среде»** `[HYPOTHESIS]` — неоднородность по часам и дням подтверждается литературой [S5][S6][S7], но конкретные окна v1 не подтверждены, а часть из них противоречит данным (см. H-10, H-11).

### I.5 Сверка цифр v1 `[OPEN]`

- DOGE: 1 004 сделки; gross `+2 711.69`; издержки `−10 575.96`; net `−7 864.27` (арифметика сходится).
- ALL8: 3 418 сделок; gross `+1 725.93`; издержки `−11 712.32`; net по этим числам `≈ −9 986` (около −100% депозита).

## ЧАСТЬ II. ДАЙДЖЕСТ ДОКАЗАТЕЛЬСТВ: ЧТО УЖЕ ИЗВЕСТНО (ресерч от 2026-11-01)

Здесь — только то, что удалось проверить по источникам на дату ресерча. Каждый пункт заканчивается следствием для документа (→). Ссылки `[S#]` раскрыты в Приложении A.

**1. Комиссии Bybit.** Обычный аккаунт: taker 0.055%, maker 0.02%; по сверке с официальными тарифами на 29.05.2026 ставки не менялись [S1].
→ Ставки v1 верны; maker — это издержка, а не ребейт.

**2. Funding.** Расчёт по умолчанию каждые 8 часов (00:00, 08:00, 16:00 UTC); платят держатели позиции на момент расчёта; у части контрактов интервал короче, у лимита ставки возможен переход на часовой [S2].
→ Интервал читать по каждому контракту из API (`instruments-info`, поле интервала funding — сверить с документацией), не хардкодить «8 часов»; funding включать в PnL (R-03).

**3. Данные Bybit под гипотезы про ликвидации и OI.** Поток `allLiquidation.{symbol}` отдаёт все ликвидации (USDT, USDC, inverse) с частотой 500 мс (раньше — одно сообщение в секунду на символ); это **real-time поток** — исторический архив придётся писать самим. Эндпоинт open interest даёт интервалы 5m / 15m / 30m / 1h / 4h / 1d, по 200 записей на страницу, и Bybit прямо предупреждает о возможных задержках при экстремальной волатильности [S3].
→ H-07 и H-19 уязвимы именно там, где задержка OI максимальна (в каскадах). Нужен собственный коллектор «point-in-time» (Часть VII, 7.9).

**4. CME перешёл на режим 24/7.** С 29 мая 2026 фьючерсы и опционы CME на криптовалюты торгуются круглосуточно; техокна — 17:00–17:02 ET в будни и двухчасовое по выходным [S4].
→ Механизм «CME-гэп» из H-11 (CME закрыт с пятницы до воскресенья) **для данных после 29.05.2026 не работает**. Любой тест H-11 обязан разделять выборку на «до» и «после» этой даты.

**5. Внутридневная структура волатильности.** Есть устойчивая периодичность волатильности и ликвидности по дню недели, часу и даже внутри часа; авторы предположительно связывают её с алгоритмической торговлей и временем funding [S5]. Свежее исследование на данных Kraken (2016–2025): девять часов `13:00–21:59 UTC` дали 50.6% дневной реализованной дисперсии BTC в 2022–2025 против 38.4% в 2016–2018; самый волатильный час сместился с 14:00 UTC (летнее время США) на 15:00 UTC (зимнее) — то есть следует за Нью-Йорком; отношение волатильности выходных к будням упало с 0.96 (2016) до 0.60–0.64 (2024–2025), объёма — с 0.78 до ~0.43–0.46. Оговорки: в основном одна биржа, данные до конца 2025 [S6; по пересказу CryptoSlate, первоисточник MDPI не открывал].
→ Сессии нужно задавать по локальному времени бирж, а не фиксированными UTC-окнами; 1 ноября 2026 США перешли на зимнее время — открытие NYSE сдвинулось с `13:30` на `14:30 UTC` (первая торговая сессия после перехода — понедельник 2 ноября; см. H-10).

**6. «Monday Asia Open Effect».** Внутридневной трендовый бенчмарк по BTC (2018–2025, vol-target 20%, Sharpe до комиссий ≈ 1.6) демонстрирует рост доходности с воскресенья около 19:00 по Нью-Йорку на ~24 часа — совпадает с понедельничным открытием Азии; эффект заметно сильнее после середины 2020 года. В воскресное американское утро — наоборот, более «рваное» движение и возврат к среднему [S7].
→ Прямо противоречит v1 («в Азию пробои на 70% ложные»). H-10 и H-11 переписаны на анализ «час недели» вместо фиксированных окон. Sharpe — до комиссий; на нетто-базу это не переносится.

**7. Трендследование работает на дневном горизонте.** Ансамбль Donchian-моделей с lookback от 5 до 360 дней и волатильностным сайзингом, BTC + альткоины [S8].
→ Стратегии v1 строятся на 15-минутных пробоях, где издержки сопоставимы с баром. Дневной ансамбль — обязательная «базовая линия», которую надо превзойти (R-01).

**8. Моментум и кросс-сечение.** Для крипты опубликованы значимые 1–4-недельные кросс-секционные факторы (рынок, размер, моментум) на горизонте недель [S9]; но при «реалистичных допущениях» (издержки, риск ликвидации) эффект тайм-серийного моментума сильный, а кросс-секционного — слабый [S10].
→ H-14 (ранжирование 8 монет на горизонте 4–24 часов) не опирается ни на одно из этих исследований; тайм-серийный (собственный тренд) фильтр надёжнее кросс-секционного.

**9. Lead-lag.** Опережение BTC над ADA на тиковых данных: от 16 до 118 секунд (в среднем около 57), со статистически значимой тенденцией к сокращению; на 1-минутных данных передача BTC → альткоины сильнее у менее ликвидных [S11].
→ Гипотеза H-15 («альты запаздывают на 1–2 пятнадцатиминутных бара») этим не подтверждается — лаг измеряется секундами и минутами и сокращается. Понижена до «только исследование».

**10. Методология валидации.** Дефлированный Sharpe поправляет на число проверенных вариантов и негауссовость [S12]; в синтетическом контролируемом эксперименте комбинаторная очищенная перекрёстная валидация (CPCV) показала меньшую вероятность переобучения бэктеста и лучшую DSR-статистику, чем walk-forward [S13] (оговорка: синтетическая среда); для «новых» факторов предложен порог `t > 3.0` вместо 2.0 [S14]; повторное использование hold-out при адаптивном анализе обесценивает его [S15]; мета-разметка (вторичная модель поверх правила) описана у López de Prado и Joubert [S16].
→ Часть III целиком.

**11. ИИ и утечки из «памяти» модели.** LLM могут дословно воспроизводить экономические и ценовые данные из периода обучения; бэктесты, где LLM участвует в решениях, на периоде до даты отсечения знаний модели загрязнены [S21]. Даже при температуре 0 ответы LLM не строго воспроизводимы [S21].
→ Протокол ИИ (Часть VII): не использовать LLM как источник цен/истории, держать lockbox из данных после даты отсечения, не ставить суждения LLM внутрь бэктест-цикла.

**12. ИИ-агенты для поиска альфы.** AlphaAgent вводит три регуляризатора против «выгорания» альфы: оригинальность (сходство AST-выражений с уже известными факторами), согласованность гипотезы и формулы (проверка смыслом) и контроль сложности [S19]; RD-Agent(Q) строит цикл «гипотеза → код → бэктест на реальных данных → анализ» с планировщиком направлений [S20] (результаты заявлены авторами на акциях, не на крипте). Живой эксперимент Alpha Arena (сезон 1, октябрь–ноябрь 2025, реальные $10 000 на модель, перпетуалы на Hyperliquid): из шести LLM четыре закончили в минусе — но выборка ~2.5 недели статистически неотличима от случайности [S23].
→ Заимствуем идеи (дедупликация гипотез, проверка механизма, бюджет сложности), а LLM в роли live-трейдера не используем.

## ЧАСТЬ III. СТАНДАРТ ДОКАЗАТЕЛЬСТВ: КАК ОТЛИЧИТЬ АЛЬФУ ОТ ШУМА

### III.1 Карточка-предрегистрация (до запуска теста)

Перед прогоном заполняется карточка (шаблон — Приложение C): опровергаемое утверждение в одно предложение; признаки «as-of»; правило; данные; модель исполнения и издержек; **заявленное число вариантов** (`N_trials`); метод валидации; критерии принятия и отклонения. Пока карточка не заполнена — тест не запускается. Критерии после просмотра результатов не меняются: новая версия — это новая карточка, и она увеличивает `N_trials`.

### III.2 Реалистичный симулятор Bybit: минимальные требования

Без этого результаты любых гипотез, особенно про исполнение (H-02…H-04), недостоверны.

1. **Комиссии по ролям ног:** maker 0.02% / taker 0.055% (настраиваемо под VIP); роль определяется типом ордера и фактом исполнения.
2. **Проскальзывание рыночных ордеров:** половина спреда + влияние на цену; калибруется по собственным исполнениям (TCA) в разрезе символ × час недели × размер; до накопления данных — консервативная таблица по классам (мейджоры / среднекап / мемкоины) `[OPEN]`.
3. **Funding:** начисляется в каждый момент расчёта для позиции, открытой в этот момент: `funding_pnl = −side · notional_at_mark · FR` (лонг платит при `FR > 0`); ставки и интервалы — из истории API по каждому символу.
4. **Типы ордеров:** market (taker + проскальзывание); post-only лимит (maker; отклоняется, если пересекает рынок); лимит без post-only (может стать taker); stop-market (триггер по mark или last — **указать явно**; taker + проскальзывание + гэп); тейк-лимит (maker).
5. **Исполнение лимитки:** только если цена **прошла сквозь** уровень (для покупки — минимум бара ниже лимита минимум на 1 тик); касание ≠ исполнение; частичные исполнения; поправка на очередь; TTL; задержка отмены. При наличии L2 и трейдов — модель очереди и задержек (например, hftbacktest [S18]).
6. **Порядок событий внутри бара:** если в диапазоне бара лежат и стоп, и тейк — считать, что первым сработал **стоп**, пока суббарные данные (1m/тики) не докажут обратное.
7. **Задержка:** решение по закрытию бара `t` → ордер уходит в `t + δ`. Исполнение по цене закрытия бара `t` недопустимо (классическая утечка); минимум — открытие следующего бара + проскальзывание.
8. **Спецификации контрактов (point-in-time):** шаг цены, шаг лота, минимальный номинал, максимальное плечо, лимиты риска, смена листинга и делистинг.
9. **Mark vs Last:** триггеры стопов и ликвидации привязаны к выбранной цене; для mark-цены использовать mark-price свечи.
10. **Маржа и ликвидация:** изолированная/кросс; цена ликвидации; проверка `расстояние до ликвидации > k × стоп`.
11. **Портфель:** лимиты одновременных позиций, маржи и чистого направленного риска; капитал и размеры пересчитываются последовательно.
12. **Данные:** OHLCV 15m + 1m (для порядка событий), OI, funding, mark/index/premium-свечи; по возможности — трейды, L2, ликвидации (пишутся самостоятельно).

### III.3 Защита от утечек (чек-лист и тесты)

**Типовые утечки:**
- решение или фильтр используют данные бара `t` (его high/low/объём/закрытие), а исполнение происходит внутри бара `t` (пример: фильтр объёма «бара отката» в H-02);
- скользящие окна и перцентили включают текущий бар там, где сигнал строится на его открытии;
- слияние старших таймфреймов: значение 1h/4h-бара доступно до его закрытия (ошибка выравнивания);
- нормировки/скейлеры/пороги подобраны на всей выборке;
- метки с пересекающимися горизонтами в обучении и тесте (нет purge/embargo);
- таймстемпы OI, funding, ratio: неясно, это начало или конец интервала; задним числом исправленные вендором данные — храните «как было на момент опроса»;
- выживший универс (8 монет, которые «живы сегодня») и подбор монет по известному будущему;
- параметры подобраны на всём периоде, а «проверка» сделана на его части;
- определения «задним числом»: «трендовый день», «победители» (MAE у выигравших сделок);
- признаки-состояния внутри сделки (`mfe_after_4bars`) использованы для модели входа `[FIX]` (в v1 лежали в одном блоке `features` с признаками входа);
- LLM-специфичное: «память» модели об истории рынка (см. Часть II, п. 11).

**Обязательные тесты (идея заимствована у инструментов lookahead-/recursive-analysis во Freqtrade [S17], их можно воспроизвести в своём движке):**
1. **Prefix-invariance (обрезание):** сигналы, посчитанные на данных `[0..t]`, должны совпадать с сигналами на полной выборке в точке `t`. Любое расхождение — утечка или рекурсивная неустойчивость индикатора (EMA/ATR с разным прогревом).
2. **Сдвиг признаков:** если сдвиг признака на −1 бар заметно *улучшает* результат — признак подсматривает вперёд.
3. **Перестановка:** при случайной перестановке доходностей/меток edge обязан исчезнуть (нулевое распределение PF/ожидания).
4. **Случайный вход («обезьяна»):** те же выходы, сайзинг и издержки, но входы случайны — отделяет альфу входа от механики выхода.
5. **Бухгалтерские тождества:** `net = gross − комиссии − проскальзывание ± funding`; сумма сделок = изменение эквити; нет отрицательного cash; плечо не превышено.

### III.4 Статистика: сколько данных нужно и как не обмануться

**Минимально обнаружимый эффект.** При стандартном отклонении результата сделки `σ(R) = 1.2R` (рабочее допущение, замените своим) минимально различимое среднее ожидание — `t · σ / √N`:

| N независимых сделок | порог t = 3 | порог t = 2 |
| :-: | :-: | :-: |
| 25 | 0.72R | 0.48R |
| 100 | 0.36R | 0.24R |
| 400 | 0.18R | 0.12R |
| 1 000 | 0.11R | 0.08R |

Следствия: правило v1 «`N ≥ 25`» от шума не защищает; чтобы увидеть ожидание `+0.1R`, нужно около 1 300 независимых сделок при `t = 3` (около 580 при `t = 2`) `[VERIFIED арифметикой]`.

**Эффективная выборка.** Сделки пересекаются во времени и коррелируют между монетами. Грубая верхняя оценка эффекта: `N_eff ≈ N / (1 + (k−1)·ρ̄)` для `k` одновременно активных позиций со средней корреляцией `ρ̄`. Практичнее агрегировать PnL по дням и тестировать дневной ряд (кластер = день).

**Доверительные интервалы:** блочный или стационарный бутстрэп по дням/неделям, а не по отдельным сделкам.

**Множественные проверки:**
- Holm/Bonferroni — консервативно, подходит при любой зависимости;
- Benjamini–Hochberg (FDR) — корректен при независимых или положительно зависимых тестах; для произвольной зависимости строже Benjamini–Yekutieli;
- ресэмплинговые max-T процедуры (White's Reality Check, Hansen SPA, Romano–Wolf) учитывают корреляцию правил;
- для «новых» находок после большого поиска — порог `t ≥ 3.0` [S14].

**Дефлированный Sharpe (DSR) и число попыток.** `N_trials` — все испытанные варианты: гипотезы × параметры × пороги × действия, **включая прошлые сессии с ИИ**. В v1 «около 400 правил» × 3 типа контрфактуального действия — это ≈1 200 попыток, а не 400. DSR [S12] поправляет Sharpe на `N_trials`, длину выборки, асимметрию и толстые хвосты.

**CPCV.** Данные делятся на `N` групп, `k` групп идут в тест: получаем `C(N,k)` разбиений и `k/N · C(N,k)` независимых траекторий (N=6, k=2 → 15 разбиений и 5 траекторий) `[VERIFIED арифметикой]`. Перед тестом — **purge** (из обучения удаляются наблюдения, чьи метки перекрываются с тестом) и **embargo** (зазор после теста: не меньше максимального времени удержания; в AFML ориентир — около 1% выборки). Результат — распределение out-of-sample метрик и `PBO` (доля случаев, когда лучшая in-sample конфигурация оказывается ниже медианы out-of-sample). В синтетическом сравнении [S13] CPCV превзошёл walk-forward по PBO и DSR-статистике; на реальных рынках гарантий нет.

**Метрика модели** — не accuracy и не AUC, а **net PnL на сигнал** с учётом издержек.

### III.5 Устойчивость и стресс

- Издержки ×1.5 и ×2; проскальзывание ×2; задержка исполнения +1 бар; «пессимистичная» модель исполнения лимиток.
- Параметры ±20% («плато», а не пик): результат не должен держаться на одной точке сетки.
- Разрезы: по символам (топ-1 символ ≤ 40% прибыли), по месяцам (топ-1 месяц ≤ 30%), по направлению (long/short), по режимам (до/после 2026-05-29; зимнее/летнее время США), по независимому критерию «тренд/боковик».
- Тест «обезьяны» (случайные входы с теми же выходами) — обязателен для гипотез выхода и сайзинга (H-20…H-25).
- Сравнение с базовой линией R-01 и с vol-targeted BTC.

### III.6 Ворота принятия (стартовые политики, не законы природы)

| Ворота | Что проверяем | Стартовый порог |
| :-- | :-- | :-- |
| **G0 Инженерия** | unit-тесты, prefix-invariance, бухгалтерия, детерминизм | всё зелёное |
| **G1 Исследование** | purged CV / CPCV + embargo; блочный бутстрэп по дням | нижняя граница 95% CI net-ожидания > 0; DSR ≥ 0.95 при честном `N_trials` (для «новых» идей — `t ≥ 3`); PBO ≤ 0.2 при ≥ 10 конкурирующих конфигураций; `N_eff ≥ 100` |
| **G2 Стресс** | ×1.5 издержек, ±20% параметров, +1 бар, разрезы | net > 0 при ×1.5 и ≥ 0 при ×2 (для кандидата в бой) |
| **G3 Lockbox** | единственный прогон по предрегистрированному критерию | выполнено; провал = идея закрыта |
| **G4 Shadow** | ≥ 4 недель или ≥ 100 сигналов на живых данных без денег | fill rate и проскальзывание в допуске от симулятора |
| **G5 Canary** | 10–25% целевого риска, ≥ 4 недель | нет срабатываний kill-switch; live-ожидание не ниже нижней границы CI бэктеста (SPRT/CUSUM) |
| **G6 Полный риск** | — | решение человека |

Пороги меняет только человек и только **до** просмотра результатов.

### III.7 Lockbox и адаптивное переобучение

Каждое обращение к одному и тому же hold-out после «подкрутки» делает его частью обучающей выборки [S15]. Для ИИ-разработки это главный риск: ассистент итеративно «улучшает» стратегию, глядя на одну и ту же out-of-sample метрику.

1. **Три слоя данных:** research (свободная работа) → validation (ограниченные обращения, каждое логируется) → lockbox (один раз).
2. **Бюджет обращений** к validation на гипотезу (например, ≤ 10); счётчик — в реестре.
3. **Грубая обратная связь:** ИИ получает по validation знак эффекта и доверительный интервал, а не десятичные знаки метрик (идея reusable holdout / Thresholdout [S15]).
4. **Forward-lockbox:** данные, появляющиеся после начала работы, дописываются в lockbox и не открываются до финала.
5. **Lockbox после даты отсечения знаний модели:** для Claude Sonnet 5.5 — период после июня 2026 года (для других моделей — по их дате). Это единственная выборка, о которой модель заведомо ничего «не помнит».

## ЧАСТЬ IV. ЭНЦИКЛОПЕДИЯ ГИПОТЕЗ v2 (25 + 4)

**Как читать карточки.** Идея (механизм) → формула/правило → что исправлено относительно v1 `[FIX]` → как тестировать → приоритет. Механизмы («что делают маркет-мейкеры») помечены `[NARRATIVE]` и в доказательство не засчитываются. Числа в карточках — **рабочие допущения**, пока в поле «Журнал результатов» нет `run_id`: все эффекты v1 вида «+0.45…+0.65 к PF», «win rate > 55%», «70% пробоев ложные» исключены как не имеющие источника.

**Модули стратегий.** `S1` — Momentum Breakout (пробой максимума/минимума Дончиана, в v1 — 20 баров 15m; стоп по ATR/структуре; трейлинг). `S2` — Mean-Reversion / Range Fade (вход против отклонения от границ канала в боковом режиме).

**Общие определения.** `ATR14` — средний истинный диапазон 14 баров; `ClosePos = (Close − Low) / (High − Low)`; `ΔOI` — изменение открытого интереса за 15 минут; `SMA(V,20)` — средний объём 20 баров; все признаки считаются «as-of» (закрытые бары ≤ t).

### ДОМЕН 1. Инженерия исполнения (Execution Alpha & Cost Reduction)
*Цель: сократить издержки на сделку. Это не «заработок на комиссии» — maker на обычном аккаунте тоже платит 0.02%.*

#### H-01 · «Порог издержек» (в v1 — «Бюджет трения»)
- **Идея** `[HYPOTHESIS]`: сделки с большой издержкой в R не окупаются — их надо отсекать либо делать с более широким стопом и меньшим плечом.
- **Формула:**
  $$\text{cost}_R=\frac{c_{in}+p_{stop}\,c^{taker}_{out}+(1-p_{stop})\,c^{maker}_{out}+s+f}{\Delta_{stop}}$$
  где `p_stop` — доля выходов по стопу (taker), `s` — ожидаемое проскальзывание, `f` — ожидаемый funding за удержание.
- **Правило:** входить, только если `cost_R ≤ θ`. Порог θ — параметр (в v1 — 0.06, `[HYPOTHESIS]`); тестировать сетку θ ∈ {0.06, 0.10, 0.15}.
- **[FIX] vs v1:** (1) «Maker-вход + Maker-тейк» для стопа неверно — стоп это taker; (2) расширение стопа до 2.67% меняет сам сетап (число сделок, удержание, funding, валовое R), поэтому «−70…−85% потерь на комиссиях» не подтверждено; (3) порог 6% произвольный; (4) опечатка в v1: «структурный стоп уже `Δstop_min`» должно быть «меньше».
- **Тест:** две реализации — A) блокировать сигналы с `cost_R > θ`; B) расширять стоп до `Δstop_min` с пропорциональным снижением размера. Оценка — net-ожидание **на сигнал**, число сделок, суммарные издержки, PF. Попыток: 3 θ × 2 реализации = 6.
- **Конфликты:** H-17, H-20, H-21 сужают стоп или закрывают сделки раньше → `cost_R` растёт (стоп ×0.68 → издержка в R ×1.47). Оценивать совместно. **Приоритет: P0, цена низкая.**
- **Журнал результатов:** —

Минимальный стоп `Δstop_min = c / θ` `[VERIFIED арифметикой]`:

| круговая издержка `c` | θ = 0.06 | θ = 0.10 | θ = 0.15 |
| :-: | :-: | :-: | :-: |
| 0.075% | 1.25% | 0.75% | 0.50% |
| 0.110% | 1.83% | 1.10% | 0.73% |
| 0.160% | 2.67% | 1.60% | 1.07% |

#### H-02 · Лимитный вход на откате
- **Идея** `[HYPOTHESIS]`: после импульсного пробоя часть сигналов даёт ретест пробитого уровня; лимитка (maker) снижает комиссию и улучшает цену. «72% ретестов» из v1 не подтверждено: измерить `P(ретест за 1–3 бара)` по символам и сессиям.
- **Правило:** post-only лимит `P = Close − k·ATR14`, `k ∈ {0.15, 0.25, 0.35, 0.45}`, TTL = 3 бара.
- **[FIX] vs v1:**
  1. Фильтр «объём бара отката < 0.85·SMA(V,20), отмена при V > 1.5·SMA» использует объём бара, который **известен только после его закрытия** — это утечка. Допустимо: объём «на текущий момент» по 1-минутным данным либо объём предыдущих баров.
  2. Исполнение — только при проходе цены сквозь уровень (III.2, п. 5).
  3. Оценивать **на сигнал**, а не на исполненную сделку: `Δ = fill_rate · E[R_filled] − E[R_market]` (неисполненный сигнал даёт 0 при лимитной политике, а его рыночный исход — «упущенная прибыль»). Иначе — «проклятие победителя»: неисполненные лимитки смещены в сторону лучших сделок.
- **Данные и тест:** журнал сигналов, включая неисполненные (6.1); 1-минутные бары; adverse selection = средний сдвиг mid против вас после исполнения. Попыток: 4. **Приоритет: P1.**

#### H-03 · Двухступенчатый вход «Разведчик + Ядро»
- **Идея** `[HYPOTHESIS]`: 30% риска входит лимиткой у лучшей цены, 70% — сеткой на откате (−0.25 и −0.50 ATR), стоп общий.
- **Риски:** при продолжении падения «ядро» исполняется и добавляет убыток; при безоткатном росте остаётся только «разведчик» → прибыль меньше. «R/R в 1.5 раза выше» не подтверждено.
- **Статус:** не тестировать до результатов H-02 (это его вариант); число попыток растёт кратно (доли × уровни). **Приоритет: P3.**

#### H-04 · Пассивный выход вместо рыночного time-stop
- **Идея** `[HYPOTHESIS]`: если сделка закрывается по времени (`max_hold_bars`) без срочности, закрывать её лимиткой на лучшей цене (post-only «chaser»), а не рынком.
- **Арифметика эффекта:** `Δc = w_time · (c_taker_exit − c_maker_exit)`. При `w_time = 35%` (доля time-stop в бэктесте v1, `[HYPOTHESIS]`), `0.055% + 0.045% = 0.10%` против `0.02%` экономия составит `0.35 × 0.08% ≈ 0.028%` (≈ 2.8 bps) на среднюю сделку — около 14–17% от `c_rt` в 16–20 bps. Полезно и безопасно, но не «чудо».

### ДОМЕН 4. Межрыночная синхронизация (Cross-Asset & Relative Strength)

#### H-13 · Фильтр «поводыря» BTC
- **Идея** `[HYPOTHESIS]`: при резком движении BTC сигналы по альткоинам против него хуже.

- **Вариант B (предпочтительнее):** остатки `r_i = α + β_i · r_BTC + ε`; сигнал строить по `ε` (BTC-нейтрально) + фильтр режима BTC.
- **Замечание:** на закрытии 15-минутного бара движение BTC уже «в цене» альта (опережение измеряется секундами [S11]) → это фильтр режима, а не предсказатель. **Приоритет: P1.**

- **Идея** `[HYPOTHESIS]`: лонги — только по лидерам, шорты — только по аутсайдерам.
- **[FIX] Формула:** v1 складывала безразмерную величину (`R/ATR%`) с `ΔOI` в процентах. Корректно: `RS_i = 0.5·z(R_4h/ATR%) + 0.3·z(R_24h/ATR%) + 0.2·z(ΔOI_4h)`, где `z` — кросс-секционный z-score (или ранг) по пулу в момент `t`; веса — начальные кандидаты.

| ↑ | ↑ | приток новых позиций, тренд | S1 по направлению |
| ↑ | ↓ | закрытие шортов (squeeze), топливо иссякает | осторожно с продолжением; кандидат для S2 |
| ↓ | ↑ | набор шортов, медвежий тренд | S1 по направлению |
| ↓ | ↓ | ликвидация лонгов (капитуляция) | не шортить дно; кандидат для S2 |

- **[FIX]:** (1) OI — сумма длинных и коротких; направление «новых денег» по ΔOI однозначно не определяется (цена↑ + OI↑ может означать набор шортов, поглощаемых пассивными покупателями) → для различения добавить знак/величину funding и дисбаланс агрессии; (2) порог `±0.2%` ненормирован — для разных монет и режимов он значит разное: `zOI = ΔOI_15m / σ(ΔOI, 672 бара)`, квадранты по `|zOI| > 1`; (3) таймстемпы OI и возможные задержки [S3]; (4) выводы «ложный пробой» и «не шортить дно» — гипотезы о продолжении/развороте, а не факты; (5) модули названы S1/S2 (в v1 — «H-1/H-2»).
- **Тест:** условные net-доходности по квадрантам (кластерные ошибки по дням), стабильность по символам и месяцам. **Приоритет: P1.**

### ДОМЕН 6. Выход и размер позиции (Exit & Sizing Alpha)
*Цель: сохранять прибыль тренда и не держать «мёртвые» сделки. Главная опасность — путать альфу выхода с альфой входа: каждая гипотеза домена проверяется тестом «случайный вход» (III.3).*

#### H-20 · Ранний аборт мёртвой сделки (4-Bar Kill)
- **Идея** `[HYPOTHESIS]`: если за первые 4 бара сделка не показала MFE и сидит в минусе, вероятность выигрыша мала → выйти до полного стопа.
- **[FIX] vs v1:** (1) пороги в тексте и в правиле разные (`MFE ≥ 0.25R` и `−0.40…−0.60R` против `0.20` и `−0.35`) — унифицировать и вынести в сетку; (2) «вероятность < 18%» и «+0.65R на **каждой** несостоявшейся сделке» не подтверждены: `0.65R` получается лишь на тех, что дошли бы до −1R; убитые сделки, которые развернулись бы, теряют потенциал; (3) лимитный выход на −0.35R не гарантирован — нужен fallback; (4) эффект считается **последовательной симуляцией на барах**, а не по журналу (ранний выход меняет путь и капитал).
- **Лучшая постановка:** оценить `P(win | состояние на баре k)` моделью (логистика/hazard) на purged CV и выбирать порог по ожидаемому net R.
- **Сравнения:** (а) с «обезьяной»; (б) с простым более узким статичным стопом (ранний аборт — это стоп, зависящий от времени); `cost_R` растёт (H-01). **Приоритет: P1.**
- **Журнал результатов:** —

#### H-21 · Стоп по 90-му перцентилю MAE победителей
- **[FIX] Логическая ошибка v1:** из «90% выигрышных пробоев не уходят глубже −0.68R» не следует «сделка в −0.75R с вероятностью > 90% проигрышная» — это перестановка условной вероятности. По Байесу:
  $$P(\text{win}\mid \text{MAE}>x)=\frac{P(\text{MAE}>x\mid\text{win})\,P(\text{win})}{P(\text{MAE}>x\mid\text{win})\,P(\text{win})+P(\text{MAE}>x\mid\text{loss})\,P(\text{loss})}$$
  Результат зависит от доли побед и от доли проигрышей, прошедших уровень `x`.
- **Прочее:** правило по построению выбрасывает ~10% победителей; распределение MAE победителей — постфактум (hindsight); новый стоп сам меняет множество победителей → пересчёт **последовательной симуляцией**, а не по перцентилю. Сужение стопа поднимает `cost_R` (H-01). Свести с H-20 в одну семью «ранний выход». **Приоритет: P3.**
- **Журнал результатов:** —

#### H-22 · Эластичный трейлинг по MFE
- **Формула (v1; арифметика проверена):**
  $$M_{trail}(\text{MFE}_R)=M_{base}\cdot\max\left(0.40,\;1-0.18\cdot\max(0,\text{MFE}_R-1.2)\right)$$
  при `M_base = 2.5`: `+2.0R → 2.14·ATR`, `+3.5R → 1.47·ATR` (v1 округляла до 1.4); минимум `1.0·ATR` достигается при `MFE ≈ 4.5R`.
- **Замечания:** единицы — расстояние трейла в ATR (цена), MFE — в R: зафиксировать явно. Четыре параметра (`M_base`, `0.18`, `0.40`, `1.2`) — бюджет сложности. Трендовая прибыль живёт в «правом хвосте», сужение трейла его режет → смотреть **capture ratio** (реализованное / MFE) и долю прибыли от топ-5% сделок, а не только PF.
- **Тест:** против фиксированного трейла и chandelier; с «обезьяной». **Приоритет: P1.**
- **Журнал результатов:** —

#### H-23 · Сайзинг по качеству сетапа (мета-разметка + Келли)
- **Идея** `[HYPOTHESIS]`: вторичная модель `p̂_win` решает, брать ли сигнал и с каким размером [S16].
- **[FIX] Формула v1:** `(p(b+1) − 1)/b` — корректная доля Келли для бинарной ставки (`f* = p − (1−p)/b`, `b` — средняя прибыль к среднему убытку), но v1 использовала её как *множитель к BaseRisk* с ограничением `[0.35; 1.5]`: размерность не сходится (`f*` обычно 0–0.3 от капитала), а нижняя граница 0.35 противоречит фразе «слабые сигналы пропускаются (0×)». Корректно: `risk_mult = clip(λ · f*(p̂) / f*(p₀), 0, m_max)`, где `λ = 0.25–0.5` (дробный Келли), `p₀` — базовая вероятность, `m_max ≈ 1.5`; при `f* ≤ 0` сигнал пропускается.
- **Условия:** (1) `p̂` должна быть **откалибрована** (Platt или изотоническая регрессия на out-of-sample, график надёжности, Brier score) — сырые баллы классификатора вероятностью не являются; (2) `b` непостоянна — лучше моделировать ожидаемый net R напрямую либо фиксировать `b` тройным барьером; (3) мета-модель добавляет ценность только при наличии информации, не использованной основным правилом — сравнивать с постоянным сайзингом и с вариантом «только фильтр»; (4) метка — тройной барьер, валидация — purged CV.
- **Приоритет: P2** (после журнала v2 и нескольких сотен сигналов).
- **Журнал результатов:** —

#### H-24 · Торговля по кривой собственного капитала
- **Идея** `[HYPOTHESIS]`: снижать риск, когда эквити ниже своей средней (EMA15) или после серии стопов по монете («карантин» `0.25R` до виртуальной/реальной прибыли `≥ +1R`).
- **[FIX]:** (1) разумно **только если результаты сделок серийно зависимы** — сначала проверить автокорреляцию R (тест Льюнга–Бокса) и поведение правила на синтетических независимых последовательностях (там оно помогать не должно); (2) EMA по 15 сделкам шумная; (3) «виртуальная прибыль» требует журнала **теневых сделок** во время карантина, иначе выйти из карантина невозможно; (4) правило добавляет лаг и зависимость от пути → оценивать по просадке и Sharpe, а не по PF. **Приоритет: P2.**
- **Журнал результатов:** —

#### H-25 · Портфельный тормоз корреляции
- **Идея** `[VERIFIED логикой]`: три лонга по сильно коррелированным монетам — это почти одна позиция с тройным риском.
- **[FIX] Формула:** v1 ограничивала сумму однонаправленных рисков (`1.8R`) — это частный случай `ρ = 1`. Общий вид: `r_i = side_i · risk_i` (в R), `σ_p = √(rᵀ Σ r)`, где `Σ` — корреляционная матрица (скользящая или «стрессовая» `ρ_ij = max(ρ̂_ij, 0.8)`); правило `σ_p ≤ R_cap`.
- **Хеджи:** «шорт по слабому активу на полный объём» — не хедж, а парная позиция с базисным риском; считать как бета-скорректированный размер.
- **Дополнительно:** маржа портфеля и одновременные стопы при гэпе. **Приоритет: P1.**
- **Журнал результатов:** —

`status ∈ {filled, expired_unfilled, blocked_by:<rule_id>, cancelled}`; `shadow_market_net_r` — исход, если бы вход был рыночным (нужен для оценки «упущенной прибыли» и «проклятия победителя»).

**Что изменено относительно v1** `[FIX]`:
- `features` разделены на `entry_features_asof` (только данные до закрытия сигнального бара) и `path` (состояния внутри сделки); в v1 `mfe_after_4bars` лежал вместе с признаками входа → утечка при обучении фильтров входа;
- добавлены `funding_usdt`, роли ног (`maker/taker`), `fill_ratio`, `trigger_price` и `avg_fill_price`, `risk_usdt_actual`, `liq_dist_pct`, версии кода/данных/модели издержек;
- `r_net` считается по **фактическому** риску на стопе; `cost_r` — отдельное поле;
- сессии — через tz-базу (`ny_minutes_since_open`, `is_us_dst`), а не строка `"us"`;
- `signals.jsonl` — журнал неисполненных и заблокированных сигналов (в v1 отсутствовал);
- признаки OI — нормированные (`oi_z_15m`) и с таймстемпом снимка.

### 6.2 Правила журнала

- Все времена — UTC, ISO-8601 с миллисекундами. `signal_bar_close` — время закрытия бара, на данных которого принято решение.
- `entry_features_asof` строятся только из данных ≤ `asof_bar_close_utc`; `path` в моделях входа **не используется**.
- `net_usdt = gross − fees − slippage + funding` (funding со знаком); `gross` считается по запланированным ценам, `slippage` — разница между запланированной и фактической ценой исполнения.
- Каждое число в отчётах привязано к `run_id`.

### 6.3 Реестры

- **`runs.csv`**: `run_id, utc_start, период данных, символы, git commit, config_hash, data_snapshot, sim_version, cost_model, N_trades, N_eff, net_R, CI95_low, CI95_high, PF, MaxDD, DSR, N_trials_на_момент_прогона, примечание`.
- **`trials.csv`**: `trial_id, run_id, hypothesis_id, variant (параметры), n_variants, purpose (explore | validate | lockbox), автор (человек | ИИ), utc`.
- **`graveyard.md`** — «кладбище» отклонённых гипотез: идея, `run_id`, причина отказа. Не даёт ИИ повторно «открывать» уже закрытые идеи (повторные проверки раздувают `N_trials`).

### 6.4 Майнинг правил v2 (замена «Subgroup Discovery» из v1)

**Почему меняем.** v1 перебирала ≈ 400 правил × 3 действия (≈ 1 200 попыток) при `N ≥ 25` и требовании «плюс в обеих половинах истории». По таблице MDE (III.4) при 25 сделках различимо лишь ожидание ≥ 0.72R — движок будет находить шум.

1. **Две стадии.** (а) *Гипотезо-управляемая* проверка карточек H/R — число условий известно заранее; (б) *исследовательская* — только после (а); результаты помечаются `explore-only` и обязаны пройти новый независимый тест.
2. **Единица анализа — сигнал** (включая неисполненные и заблокированные), кластер — день.
3. **Метрика эффекта:** разность net-ожидания в R и в bps с блочным доверительным интервалом.
4. **Размер выборки:** `N_eff ≥ 100` на правило; для подгрупп рядом с эффектом всегда показывать MDE.
5. **Множественные проверки:** Holm / BH-BY / max-T; порог `t ≥ 3` для новых находок; `N_trials` — в DSR.
6. **Устойчивость:** знак эффекта положителен минимум в 5 из 6 временных блоков **и** у ≥ 70% символов; параметры ±20% («плато»).
7. **Сложность:** ≤ 2 условий; правило монотонно и имеет экономический смысл; штраф за число порогов (идея controlled complexity из AlphaAgent [S19]).
8. **Дедупликация:** новое правило не должно быть сильно скоррелировано с уже принятыми (корреляция сигналов, перекрытие сделок) — аналог «оригинальности» [S19].

### 6.5 Что считается по журналу, а что — только пересимуляцией

| Тип изменения | По журналу (приближённо) | Требует пересимуляции на барах/тиках |
| :-- | :-: | :-: |
| Фильтр входа (блокировать сигналы) | да, без учёта влияния на капитал и пересечение позиций | для точного эффекта на эквити и портфель |
| Тип ордера входа (лимит вместо рынка) | нет | да: fill-модель, неисполненные сигналы |
| Стоп / трейл / time-kill | нет: MAE/MFE не хранят порядок событий | да: путь по барам, порядок внутри бара |
| Размер позиции | частично (масштабирование R) | да: эквити, маржа, портфельные лимиты |

`[FIX]` v1 утверждала, что движок «мгновенно считает» контрфактуальный эффект блокировки, перевода на лимит и поджатия стопа по журналу; для двух последних типов это неверно.

### 6.6 ML-слой (мета-разметка): как делать правильно

Журнал сигналов v2 → метки тройным барьером (с `t1` для purge) → признаки as-of → простая модель (градиентный бустинг с ограничением глубины) → purged CV / CPCV → калибровка вероятностей → net-PnL **на сигнал** при выбранном пороге → сжатие в правила глубины ≤ 2 (SHAP / деревья) для интерпретации → сравнение с простым фильтром и с постоянным сайзингом → DSR с учётом `N_trials` (включая число гиперпараметров). Старт — когда накоплено несколько сотен независимых сигналов (по MDE).

### 6.7 Контур изменений вместо «автоприменения патча»

`[FIX]` В v1 система сама формировала `bot_live_config.json` и применяла «подтверждённый» патч к боевому роботу. Это недопустимо: автоприменение превращает ошибку поиска в реальные потери.

**v2:** *предложение изменения* = карточка + diff конфига + предрегистрированные критерии → ворота G0…G6 (III.6) → **человек** подписывает переход в canary/full → мониторинг live-ожидания относительно доверительного интервала бэктеста (SPRT/CUSUM) → автооткат → запись в реестр. **Бюджет изменений:** не более 1–2 изменений параметров в неделю (ограничение адаптивности, III.7).

**Kill-switch** (жёсткие лимиты, независимые от стратегии и от ИИ): дневной лимит убытка; число стопов подряд; отклонение fill/проскальзывания от модели; пропуск данных дольше N секунд; ошибки API; превышение чистого направленного риска → закрыть позиции и остановиться.

## ЧАСТЬ VII. ПРОТОКОЛ РАБОТЫ ИИ-РАЗРАБОТЧИКА (как помочь нейросети работать лучше)

**Принцип.** Качество результата ИИ определяют не только «ум» модели, а четыре вещи: что она **видит** (контекст), чем может **проверить себя** (верификация), что ей **запрещено** (инварианты) и как устроен **цикл работы**. Это согласуется с практикой Anthropic [S22]: дать модели способ проверить результат (тесты, прогоны), отделять исследование от реализации, держать постоянные инструкции короткими и помнить, что контекст конечен и качество падает по мере его заполнения.

### 7.1 «Конституция проекта» (шаблон для `CLAUDE.md` / `AGENTS.md` / системной инструкции)

Короткий файл, который загружается в каждую сессию. Команды ниже — примерные, подставьте свои.

```markdown

## Цель
Найти и безопасно внедрить стратегии USDT-перпетуалов Bybit с положительным ожиданием NET
(после комиссий, проскальзывания и funding), подтверждённым вне выборки.
Прибыль на бумаге без этого — не результат.

## Инварианты (нарушать нельзя)
1. Все числа в отчётах — из прогона (run_id). Не вспоминай и не оценивай «на глаз».
2. Метрики только net; gross — только рядом с разложением издержек.
3. Признаки только as-of (закрытые бары ≤ t). Сомнение = пиши тест на утечку.
4. Lockbox (последние N месяцев + данные после даты отсечения знаний модели) не открывать
   до решения человека.
5. Каждый прогон → runs.csv и trials.csv (даже неудачный). Отклонённые идеи → graveyard.md.
6. Время: хранение UTC; сессии через tz-базу (America/New_York, Europe/London, Asia/Tokyo).
7. Исполнение пессимистично: лимитка — только при проходе цены сквозь уровень;
   стоп = taker + проскальзывание; funding начисляется на расчётах.
8. Названия: стратегии S1/S2…, гипотезы H-xx / R-xx. Суффиксы единиц: _pct, _bps, _r, _usdt.

## Команды (примерные)
- Тесты:   pytest -q
- Утечки:  python tools/leak_check.py --strategy S1
- Бэктест: python run_backtest.py --config configs/s1.yaml --seed 42
- Отчёт:   python tools/report.py --run RUN_ID

## Формат отчёта (обязателен)
run_id · период · символы · N сделок и N_eff · net-ожидание (R и bps) + 95% CI ·
доля издержек от gross · PF · MaxDD · стресс ×1.5/×2 · N_trials · вывод
«принять / отклонить / нужны данные» · минимум 3 пункта «что может быть не так».

## Рабочий цикл
Explore → Plan (письменно; для изменений ядра жди подтверждения) → Implement малыми шагами →
Verify (тесты + отчёт) → Report. Если неясно (единицы, таймстемп, определение R) — спроси.

## Состояние
Читай STATE.md в начале сессии, обновляй в конце.
```

| Этап | Что делает ИИ | Артефакт | Контроль человека |
| :-- | :-- | :-- | :-- |
| **Explore** | читает код и данные без изменений; перечисляет допущения; составляет карту данных | список допущений и вопросов | — |

### 7.3 Верификационная обвязка (чем ИИ проверяет себя)

1. Юнит-тесты индикаторов против эталона (особенно определения ATR: Wilder или простая SMA — зафиксировать).
2. Prefix-invariance и тест рекурсивных индикаторов (разный прогрев EMA/ATR) [S17].
3. Тест сдвига признаков (−1 бар не должен улучшать результат).
4. Тест перестановки (edge исчезает на шуме).
5. «Обезьяна»: случайные входы с теми же выходами, сайзингом и издержками.
6. Кривая «издержки ×0 / ×1 / ×1.5 / ×2» — результат должен деградировать плавно.
7. Сравнение «оптимистичное vs пессимистичное исполнение».
8. Бухгалтерские тождества (PnL, эквити, плечо, R).
9. Тесты времени и DST: даты 2026-03-08, 2026-03-29, 2026-10-25, 2026-11-01.
10. Детерминизм: одинаковые код, конфиг, данные и seed → одинаковый хэш списка сделок.
11. Качество данных: пропуски, дубли, выбросы, смена спецификаций, делистинг, point-in-time вселенная.
12. Регрессионные «золотые файлы»: ключевые метрики эталонного прогона; изменение при правке кода должно быть объяснено.
13. Ручной аудит: 10 случайных сделок сверяются с графиком.

### 7.4 Что давать ИИ на вход (и что нет)

**Давать:**
- короткую конституцию (7.1) и индекс документа; нужные карточки по ссылке, а не весь файл;
- возможность **исполнять код** и читать результаты (иначе числа будут «из головы»);
- официальную документацию API Bybit по ссылке на момент задачи (интервалы, поля, лимиты);
- словарь терминов и единиц (R, `cost_R`, as-of, `N_eff`);
- хорошие и плохие примеры отчётов; «кладбище гипотез»; журнал решений;
- сжатые **слепки** вместо сырых журналов: разложение издержек, карта «час недели», матрица причин выхода, корзины признаков с доверительными интервалами и MDE.

**Не давать / не просить:**
- «вспомни, как BTC торговался в 2021» (память модели об истории — источник утечки [S21]);

### 7.7 Контекст-инженерия: как «кормить» ИИ этим документом

Контекст — конечный бюджет внимания: нужен минимальный набор значимых токенов, а длинный контекст ухудшает качество [S22].

1. **Разбить файл на модули:** `00_index.md` (Часть 0, карта, таблица статусов P/статус), `10_costs.md` (I), `20_evidence.md` (II), `30_standard.md` (III), `40_hypotheses/H-xx.md` (по карточке), `50_telemetry.md` (VI), `60_ai_protocol.md` (VII), `90_sources.md`. ИИ загружает индекс и нужные модули по мере необходимости.
2. **`STATE.md`** — структурированные заметки вне контекста: цель, решения с причинами, результаты (`run_id`), открытые вопросы, следующий шаг; обновляется в конце каждой сессии.
3. **Изоляция задач:** аудит, литературный поиск, ревью кода — отдельными сессиями или субагентами; наружу возвращается сжатое резюме.
4. **Слепки вместо сырых журналов** (для кнопки «Сформировать слепок для ИИ» в дашборде): агрегаты с доверительными интервалами и MDE, а не списки сделок.
5. **Конституция короткая:** только то, что применимо всегда; остальное — по ссылке.

### 7.8 Роли ИИ и границы

**Где ИИ полезен:** генерация и критика гипотез; написание и ревью кода; тесты; документация; анализ результатов по цифрам из прогонов; поиск литературы.

**Где ИИ не должен быть:** источником цен и исторических фактов; принимающим live-решения; меняющим лимиты риска; подписывающим переход между воротами; интерпретирующим «на глаз» без `run_id`.

**Live-торговля:** детерминированный протестированный код + жёсткие лимиты (kill-switch, 6.7). Эксперимент Alpha Arena показал, что LLM в роли live-трейдера на коротком интервале легко перерабатывает сделками (издержки), а результаты ~2.5 недель статистически малоинформативны [S23].

**Паттерны из исследований:** цикл «гипотеза → реализация → бэктест → анализ» с планировщиком направлений [S20]; три регуляризатора против «выгорания»: оригинальность (дедупликация), согласованность гипотезы и формулы (проверка механизма) и контроль сложности [S19]. Адаптация: бюджет попыток, лимит параметров, обязательное сравнение с уже принятыми правилами.

**Многоагентность** (по мере роста задач): Исследователь, Инженер, Аудитор (независимый контекст: видит данные и код, но не выводы Исследователя), Риск-офицер (проверяет лимиты). Дороже по токенам — для рутины достаточно одного ассистента с чек-листом.

### 7.9 Данные и инфраструктура

- **Что записывать** (Bybit WS/REST): публичные трейды (с флагом стороны), стакан L2 (снимки + дельты), тикеры (mark, index, funding, OI), mark/index/premium-свечи, `allLiquidation`, `instruments-info` (спецификации и интервал funding), собственные ордера и исполнения (TCA).
- **Формат:** Parquet по дням и символам; метки времени биржи и приёма; контроль пропусков; неизменяемость сырых данных; манифест `data_snapshot`.
- **Зачем:** потока ликвидаций «как было» ретроспективно нет, OI может запаздывать и пересчитываться [S3]; кроме того, нужны реальные исполнения для калибровки проскальзывания.
- **Инструменты:** hftbacktest — симуляция очереди и задержек по тиковым данным (есть примеры для Binance Futures и Bybit) [S18]; идеи проверок lookahead-/recursive-analysis из Freqtrade [S17] — как эталон для собственного движка.
